Linkwright — Keeps your mods linked when versions drift

Tired of a pack refusing to start because one mod wants version 1.3 of another and you have 1.2?

Mods often pin the exact version range of another mod they integrate with. The moment that other mod updates, NeoForge stops the game with "Mod X requires Y 1.3.0 or above, and below 1.4.0" — even when the code the first mod actually uses is unchanged, or changed in a way that's trivial to bridge.

Linkwright checks the real code links between the two mods, lets the game launch when they line up, and patches the small differences in memory as the classes load. It's a temporary bridge: it keeps your mods working until their authors update, and once they do, Linkwright simply has nothing left to do.

Nothing is ever written to any mod's jar. No configuration needed. Just drop it in.

✦ How It Works

On every launch, before NeoForge checks dependency versions, Linkwright:

  1. Finds the broken rules. Reads every mod's neoforge.mods.toml (including jar-in-jar mods) and lists the mod-to-mod version rules that aren't met. Rules about Minecraft and NeoForge themselves are never touched.
  2. Checks every link. Walks the dependent mod's bytecode and resolves every class, method and field it uses in the other mod, through inheritance all the way into Minecraft and NeoForge. Mixins into the dependency are checked too: targets, injectors, @At targets, shadows, accessors and invokers.
  3. Adapts what changed. When something changed shape, it looks for exactly one safe way to adapt it and patches the dependent mod's class as it loads.
  4. Approves or refuses. If every link checks out, the rule is approved and the game launches. If anything is missing, NeoForge's normal error stays — and the report tells you exactly what's missing and why.

A full pack of 300+ mods is analyzed in about a second.

✦ What It Can Patch

  • New parameters — a method or constructor gained parameters, anywhere in the list. Linkwright keeps the old arguments in order and fills each new one from values the calling code already has (one of its parameters, or a getter on one).
  • Changed types — a parameter, return value or field changed type. Linkwright converts the value right at the call, as long as nothing can be lost.
  • Interface methods with new types — an interface now requires a method with different types. Linkwright adds that method to the mod's class, passing through to the mod's own method of the same name.
  • Return values added to void methods — the extra result is quietly discarded.

Lossless conversions only: subtype to supertype, number widening (int → long, float → double…), boxing and unboxing, BlockPos ↔ long, ChunkPos ↔ long, ResourceLocation ↔ String, and Vec3i → BlockPos.

✦ Real Examples

  • CBC Aeronautics Missiles 0.2.0 + Create: Radars 5 — Missiles pins Radars to 0.4.x. Radars 5 added a Level parameter to isInSafeZone. Linkwright verifies the other 124 links and patches both calls, passing in the level the calling code already has.
  • Power Grid 0.6.2 + TFMG 1.2.0 — Power Grid wants TFMG 1.3, which switched block positions from a packed long to BlockPos. Linkwright converts the position Power Grid passes to TFMG's constructor, and gives Power Grid's connector the long getPos() TFMG 1.2 expects.

✦ Safe by Design

  • It never guesses. If more than one fix is possible, or none is, the rule is refused and reported instead of patched.
  • It respects intentional incompatibilities. If a mod deliberately refuses to load next to another (an incompatible rule, or a check in its own code), that's the author's call. Linkwright leaves it alone.
  • It never narrows. No long → int, no casting a supertype down, no inventing numbers for new primitive parameters.
  • It's fully transparent. Every decision is written to logs/linkwright-report.txt, including every patch it made and a ready-made dependencyOverrides line if you'd rather ship the approval without Linkwright.

✦ Installing

Drop the jar into mods/ on the client, the server, or both. Linkwright runs as an early loader service, so it won't appear in the in-game mod list and never has to match between client and server — each side checks its own mods.

Note: client and server still need matching versions of the mods themselves to connect. Linkwright fixes version rules between mods, not differences between your client and a server.

✦ Configuration

config/linkwright.toml is created on first launch. The defaults are what most people want.

  • mode — "auto" (default) approves verified rules and applies patches; "report" only writes the report; "off" does nothing.
  • bridgeCalls — true (default) applies patches. Set to false to only approve exact matches.
  • ignore — rules to leave alone, written as "dependent->dependency".
  • forceApprove — rules to approve even when problems are found. This can crash your game; use only if you know what you're doing.

✦ Limits

  • Linkwright checks signatures, not behaviour. A method that keeps its signature but changes what it does still passes.
  • Removed methods with no same-named replacement, and renamed classes, can't be adapted.
  • Calls made from mixin classes or through method handles can be verified but not patched.

✦ Requirements

  • Minecraft 1.21.1
  • NeoForge 21.1
  • No dependencies.
